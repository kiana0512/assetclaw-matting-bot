# 06 性能与可靠性优化路线图

## 总体原则

当前最大收益顺序是：**先修一键流程与状态机可靠性 → 补齐可观测性 → 消除空转与单帧卡死 → 做节点级调度优化 → 最后再微调算法速度。** 如果先改模型或 FFmpeg，很可能优化错对象。

## P0：1–2 天内

### 1. 恢复一键流程可用性

- 修复飞书多维表格 app/token/scope 配置，在启动时做预检，不要运行到抽帧才失败。
- worker 启动后写 heartbeat；父进程发现退出时记录 exit code、stderr、last stage，而不是只写“僵死已清理”。
- 流程 stage 写入 `queued_at/started_at/finished_at/status/error/attempt`。
- 先用一个最小工作流跑通 DONE，并保留完整七步事件，随后才开放批量入口。

验收：连续 10 个最小流程成功率 ≥90%，每个流程 100% 有 stage 时间。

### 2. 修复 DONE 与投递回执

- 任务只能在飞书消息/云盘 API 返回 ack 后进入 `DONE`。
- 保存 `delivery_method`、目标、file/message id、upload_started/finished、send_ack_at、HTTP/业务码。
- 对历史/异常的“产物完成但回执缺失”使用 `OUTPUT_READY`，不要直接视为已投递。

验收：新成功任务 delivery receipt 覆盖率 100%。

### 3. 处理超长空转

- Cherry/worker 每 30 秒 heartbeat；active task 5 分钟无心跳自动 failover 或恢复。
- 记录每次 restart/resume；将 attempt envelope 与 active time 分开。
- 页面和告警以 `idle_gap` 为独立指标。

验收：不再出现 >10 分钟无解释 idle gap；恢复必须能追到原因。

## P1：3–7 天

### 4. ComfyUI 卡死的可恢复执行

- 单 prompt 软超时后查询 GPU/Comfy 健康；硬超时后重启对应 worker。
- 失败帧单独重排，已完成帧 checkpoint，不让单帧击穿整批。
- 本机连续卡死达到阈值时熔断并自动转集群。
- 超时阈值按像素、模型版本和历史 P99 动态设定；保留绝对上限。

验收：ZIP 因单帧超时导致的整批失败率下降 80%，恢复任务不重复已完成帧。

### 5. 拆分队列与执行时间

对本机和集群都记录：`queue_entered/worker_assigned/execution_started/execution_finished`。抽帧另记录 start/end。这样才能判断：

- 是抽帧慢；
- 是本机单 GPU 等待；
- 是远端 scheduler 等待；
- 还是纯 GPU 慢。

验收：新任务 95% 以上可把端到端时间归到互斥阶段，且时间线不交叉。

### 6. 改造分析页数据源

- 服务端分页/按时间查询，不使用前端固定 `limit:20` 代表总体。
- 所有卡片显示 cohort 起止时间、样本数、截断状态和数据可信度。
- 读取 `comfyui_runs.options_json.gpu_control` 与 Cherry attempt 数据。
- 流程、直发分开展示成功率和耗时。

验收：页面全量筛选结果与审计脚本数量、P50/P90 一致。

## P2：1–2 周

### 7. 集群调度与节点拖尾优化

- 每节点记录 frames、GPU seconds、P50/P95 帧延迟、显存、利用率、温度/功耗、并发任务。
- 分片按节点历史 Mpixel/s 加权，不按等帧数；异构 4090/3090 尤其需要。
- 小任务减少调度/模型加载开销；大任务用动态 work stealing。
- 对最后少量慢帧做 speculative execution，先完成者生效。
- 模型常驻、输入预取、结果并行回传，避免 GPU 间隙。

验收：同一基准集三节点 P90 加速 ≥2.2×、中位 ≥2.7×，straggler 占比 <15%。

### 8. 后处理与投递优化

- Cherry 浏览器池常驻，启动失败自动换实例而不是每任务冷启动。
- 序列按批次并行但限制内存；打包与部分上传可流水线。
- 飞书大文件分片/重试记录指数退避和限流响应；小文件 >60 秒直接告警。

验收：视频后处理 active P90 降低 20%；小于 10 MB 投递 P95 <60 秒。

## P3：持续优化

### 9. 容量规划

使用到达率、每类任务帧数/像素分布与每节点服务率做离散事件模拟或排队模型。不要直接用“3 台 GPU = 3 倍容量”，因为异构节点、批次大小和失败重试会降低有效容量。

### 10. 质量与速度联合指标

性能优化必须同时抽样 alpha 边缘质量、漏抠率和输出完整率。避免通过降分辨率或改模型得到更快数字，却牺牲可用质量。

## 预期收益

| 改动 | 主要收益 | 对当前问题的直接作用 |
|---|---|---|
| heartbeat + resume 事件 | 消除无解释长空转 | 解决 38–42 小时异常归因 |
| checkpoint + 单帧重排 | 提升批次成功率 | 解决 ZIP 600 秒失败簇 |
| 真实 delivery ack | 可证明完成 | 解决 105 个 DONE 无回执 |
| queue/execution 分离 | 正确定位慢点 | 不再把排队说成抽帧或 GPU |
| 节点级加权分片 | 减少拖尾 | 改善集群波动与慢任务 |
| 全量分页 + cohort | 统计可信 | 不再用 43 条代表全部 |

## 不建议立即做的事

- 不要因为当前“创建与抽帧”P90 很高就先优化 FFmpeg；该段混入本机排队。
- 不要根据全局 queue depth 扩容 scheduler；真实远端排队中位仅 0.61 秒。
- 不要只比较任务总分钟数判定 GPU 速度；必须按帧/像素与纯执行时间归一化。
- 不要在流程 0 成功时优化流程 P90；先修可靠性和事件记录。
