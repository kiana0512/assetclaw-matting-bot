## 3. 时间轴定义

直发任务按可用时间点拆为：

1. `source_download_to_task_create`：源文件 mtime 到父任务 `created_at`，仅作附件落盘后的近似延迟。
2. `prepare_or_extract`：父任务创建到 ComfyUI handshake/运行创建。视频里可能混有本地执行队列等待，不能等同于纯抽帧。
3. `matting_combined`：抠图阶段的父任务包络时间。
4. 集群专用四段：客户端准备上传、远端真实排队、GPU 执行、结果发布返回。
5. `handoff`：抠图结束到 Cherry 首次尝试，可能包含角色确认或 worker 调度。
6. `postprocess_envelope`：Cherry 最早开始到最晚结束的总包络。
7. `postprocess_attempt_sum`：所有 Cherry 尝试的实际运行时间之和。
8. `postprocess_idle_gap`：包络减去实际运行；用于识别重启、离线、恢复及重试间隔。
9. `delivery_after_post`：后处理结束到可发现的投递/任务结束时间。
10. `e2e_task`：父任务 `created_at` 到投递时间或终态更新时间。

## 4. 统计方法

- 端到端 P50/P90：使用全部 125 个成功直发任务。
- 阶段 P50/P90：只使用 115 个时间点单调递增的成功任务。
- 10 个旧任务存在阶段时间交叉或阶段和超过任务生命期；保留其端到端值，但不纳入阶段基线。
- 异常检测：按任务类别与后端分组，对端到端、阶段耗时和单位吞吐使用 median/MAD 稳健 Z 分数；明细见 `robust_outliers.csv`。
- 集群速度：只使用 SQLite 中存在 `gpu_control.started_at/finished_at` 的成功视频，从而排除上传、排队、下载和本地解压。
- 本机速度：使用逐 prompt 完成时间样本计算每帧延迟及吞吐。

## 5. 数据可信度分级

| 结论 | 可信度 | 原因 |
|---|---|---|
| 父任务数量、最终状态、父任务端到端 | 高 | 状态文件直接记录 |
| 集群远端排队/GPU 执行 | 高（有 `gpu_control` 的样本） | 远端创建、开始、结束、发布时间齐全 |
| 本机逐帧速度 | 高（有 prompt_map 的样本） | 逐 prompt 运行时间 |
| Cherry 实际工作时间 | 高（有 attempt 的样本） | SQLite 记录每次尝试开始/结束 |
| 抽帧纯耗时 | 低 | 父任务创建到 ComfyUI 创建之间混入本地队列等待 |
| 飞书收到到附件下载完成 | 不可计算 | 缺独立业务时间点 |
| 一键动画七步耗时 | 不可计算 | 26 个流程的 stage 均无开始/结束时间 |
| 已成功投递比例 | 低 | 125 个 DONE 中只有 20 个留下可发现的持久投递回执 |

## 6. 关键限制

1. 状态 JSON 是最终快照，不是追加式事件历史；进程重启期间的状态变化可能丢失。
2. `brain_messages.created_at` 更接近路由/响应写入，并非原始飞书事件抵达，不能替代 ingress 时间。
3. GPU 样本没有统一记录输入分辨率、总像素、模型参数、冷/热缓存、同时并发数，因此现有对比是运行态审计，不是严格实验室基准。
4. 三节点由 4090 与 3090 组成，节点异构；工作分配与慢节点拖尾都会影响“3 倍”期望。
