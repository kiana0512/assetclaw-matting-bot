## 1. 一句话结论

这次 97 帧任务总耗时 **50 分 10 秒**，其中 GPU 集群父批次从开始执行到完成用了 **41 分 21.434 秒，占端到端总耗时 82.44%**。批次只排队 **0.639 秒**，49.7 MB 输入上传约 **1.29 秒**，209 MB 结果下载约 **1.87 秒**，97 帧全部一次成功、没有重试、没有失败、没有客户端轮询异常。

所以准确说法是：**本次没有出现排队、失败或网络型异常，但暴露了一个稳定存在的 GPU 服务吞吐问题。**

- 4090 完成的帧数最多，说明调度器很可能在进行动态领任务，快卡获得了更多工作。这种不均匀分配本身不一定是错误。

### 不能从现有数据推断什么

- 不能断言 3090-b 一定发生了硬件故障或降频。
- 不能知道某一帧是否极慢、最后是否有长尾帧。

## 7. 根因树

### 已证实的直接根因

**GPU Control 内部实际服务吞吐低。** 97 张 1080×1440 图片进入正确版本的 `imageclip-rgba` 工作流后，三节点合计运行 41 分 21 秒才全部完成。

### 强推断，但仍需 GPU 端日志确认

1. **当前单卡工作流吞吐偏低。** 即使三节点均投入，集群总吞吐仍只有 2.345 帧/分钟。
2. **节点性能存在明显异构。** 4090 领取 49 帧，而两台 3090 分别为 28 和 20 帧；3090-b 应被单独体检。
3. **调度很可能是单帧、小粒度动态领任务。** 分配量随节点快慢变化是正向信号，但当前可能仍是每 GPU 单 prompt 串行，未把显存和计算并发拉满。
4. **全分辨率输入可能放大成本。** 输入是 1080×1440，而后处理最终为 384×512。若 ImageClip 工作流从头到尾按原始分辨率处理，150.85 MP 的总输入像素会形成显著成本。

### 当前无法证明的底层根因

- ComfyUI 是否每帧重复加载模型或冷启动。
- 工作流中哪个节点占比最大。
- GPU 利用率是否长期低于 90%，是否受 CPU 解码、磁盘或网络共享盘限制。
- 3090-b 是否温度、功耗、P-State、PCIe、显存或进程异常。
- 尾部最后几帧是否产生 straggler，导致另外两台 GPU 空等。

## 10. 优化优先级

### P0：先补数据，再调性能

- GPU Control 必须返回逐帧、逐节点、逐工作流节点时间；这不是普通监控增强，而是定位 41 分钟根因的必要条件。
- 在同一个批次 ID 上保留原始 worker/Comfy/NVML 日志，避免任务完成后只有汇总分布。

### P1：立即检查 3090-b

- 对比两台 3090 的相同 20 张固定图片基准，验证 p50/p95、GPU 利用率、功耗和模型加载时间。
- 若 3090-b 明显退化，先降低其调度权重或隔离，修复后再恢复；不要让慢节点制造尾部等待。

### P1：把模型与工作流常驻

- 确认三节点模型、ImageClip 权重和自定义节点不在每帧重复加载。
- worker 启动时预热固定样本；只有预热通过才对外报告 idle/ready。

### P1：验证单卡并发与显存利用率

- 分别测试每 GPU `1/2/3` 个并发 prompt，记录吞吐、p95 和显存峰值。
- 目标是提高总吞吐，而不是只看单帧延迟；发生 OOM 或尾延迟显著变差则回退。

### P1：做分辨率 A/B

- 以本次 97 帧复制样本，对比原始 1080×1440 与保持比例的较低工作分辨率。
- 最终结果仍按 384×512 Cherry 规则生成，并使用现有逐帧 identity、alpha 边缘和视觉回归门禁。
- 未通过发丝、半透明边缘和动作连续性验收前，不应直接上线降采样。

### P2：消除尾部等待

- 返回每节点剩余任务与预计结束时间。
- 对最后少量长尾帧启用幂等的推测执行或重新分配，首个合格结果胜出。
- 结合节点历史 EWMA 吞吐动态设置权重，而不是固定平均分片。
